# ColorPiano Pro

**用耳朵"看"颜色。**

> [English README](README.md)

大约每 12 个男性、每 200 个女性中就有 1 位无法可靠区分红色和绿色。他们的视力本身没有整体性的
退化，他们缺的是一条特定的信息通道：熟番茄和生番茄、刹车灯和尾灯、一根红线和一把灰线、
警告标签和普通标签，区分它们的东西就落在这条通道上。

这个程序让你改用听觉去听那条通道。

把摄像头对准一个物体，画面中央的颜色就变成一个钢琴音。钢琴有 52 个白键，而 52 这个数量
远多于任何一种语言提供的颜色名。每种颜色对应一个音，色觉障碍用户可以学会用耳朵认出其中
任何一个，分辨精度超过他的眼睛能给的。

针对这个问题，常规的无障碍做法是把颜色用词说出来，或者在旁边画个符号。本项目也做这件事，
但词太粗。"绿色"和"蓝色"各自要覆盖一大片颜色空间，而那恰恰是色觉障碍者最需要细分的区域。
要一个词，得到的答案比问题本身还粗。音高没有这个问题：没受过训练的耳朵也能轻松分开几十个音高，
所以用户拿到的是量具而不是字幕。不是"那偏绿"，而是"那是 D4，旁边那个是 F4"，
足够用来分类、配对和区分。

代码里其余的部分都是为了让这件事可靠：站得住的颜色数学、一组两两之间不会挨得太近的颜色、
音高不够用时补上的线索，以及在程序自己也不确定的时候能说出"我不确定"。

```
python main.py                                  # 用摄像头跑起来
python main.py --source synthetic               # 没有摄像头也能跑
python main.py --selftest --pipeline            # 自检 + 端到端测试
```

## 工作原理：通向耳朵的四条通道

一种颜色变成四个独立信号，用户能用上几条就用几条。

| 通道 | 编码什么 | 机制 |
|---|---|---|
| 音高 | 哪种颜色 | 52 个音对应 52 种颜色。颜色索引直接对应音索引，所以音高是一个稳定、可习得的标识，而不是随意的标签。 |
| 响度 | 明度 | 音符力度跟随 CIELAB 的 `L*`（`0.35 + 亮度 × 0.85`，截断到 0.15–1.0）。明度是所有色觉类型都保留的维度，所以它给另外三条做基准。 |
| 节奏（earcon） | 纹理类别 | 8 种纹理图案各有 1 到 8 个短脉冲、间隔 75 ms 的动机。偶数图案上行，奇数图案下行，每个脉冲音高递增 12%。两个维度，让动机能单凭听觉区分。 |
| 语音 | 用词说出的颜色 | 装了 TTS 引擎时："dark vivid orange, note D4, pattern diagonal"。用词刻意啰嗦，因为"dark vivid orange"携带的信息是 `#A0522D` 没有的；并且限速到约每秒一次。物体在动的时候，连续不断的语音是噪音，不是信息。 |

音高是主通道。另外三条的存在是为了解决两种情况：两种颜色落在相邻音上，或者用户想要一次确认。
三条里最重要的是纹理动机，因为图案是唯一能穿透所有色觉类型的线索，所以它同时有视觉和听觉
两种表达。

语音在两个方向上都安静降级。没有 TTS 引擎时程序改放图案音效，照常工作。引擎装了但起不来时，
它会说明原因然后闭嘴，而不是抛异常。`announce.py` 里没有任何模块级的语音库导入。
一件无障碍功能变成 import 报错，比没有这个功能更糟。

## 它做了什么

- 52 个音对应 52 种颜色。那 52 个 `*.wav` 是一台标准 88 键钢琴的全部白键（A0–C8，
  88 键钢琴正好有 52 个白键）。颜色按色相环绕一圈分成 52 份，音按音高从低到高排序。
- 用 CIEDE2000 做颜色匹配。这是按人眼感知差异标定的色差公式，不是 RGB 算术。实现经过
  已发表的参考数据校验。
- 调色板是算出来的，目标是在色觉障碍者眼里也保持分离，而不是挑 8 个安全色相再用明度铺开。
  最差情况色差 4.87，可混淆颜色对 0 对；朴素的等距色环是 0.00 和 52 分之 48。
- 每种颜色都带一个纹理图案，用图着色分配，让难分的颜色拿到不同图案。52 个颜色里只有 2 个
  和自己难以区分的邻居共用图案。
- 运行时报告歧义。如果当前颜色在你的色觉下和另一个音难以区分，屏幕会说出来，报出那个音，
  并指明该看哪个图案。
- 实时色觉模拟与增强，只作用于预览画面。
- 全部功能都能用键盘和鼠标操作。手势是附加项。整套管线在没有摄像头、麦克风和语音引擎的
  机器上也能测。

## 算法与技法

### CIEDE2000，真的实现对了

这类项目的颜色匹配通常就垮在这里。常见的偷懒写法是：

```python
lab = cv2.cvtColor(np.uint8([[bgr]]), cv2.COLOR_BGR2LAB)[0][0]
```

OpenCV 返回的是 8 位 Lab：`L` 被压到 0–255 而不是 0–100，`a`/`b` 也是 0–255 而不是
大约 −128 到 127，还附带 uint8 取整误差。后果比看上去严重，因为 CIEDE2000 的加权函数是按
`L∈[0,100]` 标定的。喂给它 0–255 的数，`S_L`、`S_C`、`S_H`、`R_T` 全都失准。
用 8 位数值跑 CIEDE2000，等于付了公式的代价却一点没拿到它的准确性，还不如直接用 RGB 距离。

`colorpiano/colorspace.py` 实现了完整的浮点链路：sRGB、线性、XYZ、CIELAB，再做 CIEDE2000。
它用 Sharma, Wu 和 Dalal (2005) 的全部 34 组标准参考数据做了校验，也就是公式发表时自带的
测试集：

```
CIEDE2000: 34 cases, 0 failures, worst error 4.95e-05
```

这个数字是一个单元测试，不是一句宣称。

### 挑选互相远离的颜色

直觉做法是挑 8 个色盲安全色相，再用明度变化铺满 52 个颜色。它行不通，原因在几何上。
把 52 个颜色按 8 个色相 × 7 个明度带摆开，同一明度带里的 8 个色相在 `L*` 上是一个圆。
二色觉者把这个圆投影成一条线，圆的两端就叠在一起了。在这种摆法上实测：52 个音里有 51 个
存在一个某些观察者分不出的邻居。

`tools/design_palette.py` 改为在观察者真正拥有的空间里工作。对每种二色觉，模拟会把颜色空间
映射到两个维度上，大致是明度加蓝黄轴。颜色用最远点采样在这个降维空间里摆放，目标是最小化
最差情况：即在正常视觉以及红色盲、绿色盲、蓝色盲之中取最小的两两色差。二色觉者看不见的
那条红绿轴，则被拿来给正常视觉做区分，在这个目标下它不占代价。

| 调色板 | 最差情况色差 | 仅正常视觉 | 有双胞胎的条目数 |
|---|---|---|---|
| 52 个等距色相 | 0.00 | 0.38 | 48 / 52 |
| `cvd_safe`（算出来的，默认） | 4.87 | 5.71 | 0 / 52 |

最差情况色差 = 在正常视觉、红色盲、绿色盲、蓝色盲里取最小，再对所有颜色对取最小。
4.87 大约是 2 个可辨差异，超过噪声和摄像头波动的量级。两套调色板都保留，
`hue` 保留是为了让用户能对照朴素摆法、亲耳听出差别（按 `p` 切换）。

测量过程中还发现那套朴素摆法一件值得知道的事：它连正常视觉都分不清。它的第 17 和第 18 号
颜色是 `(0,255,9)` 和 `(19,255,0)`，CIELAB 色相差 0.6°，色差 0.38。在 sRGB 色域的绿色角落
附近，HSV 色相的 6.92° 步长映射到 Lab 色相上只剩 0.45°，而在别处同样的步长值 25°。
所谓"52 个等距色相"并不等距。

### 用图着色分配纹理图案

每种颜色还带 8 种纹理图案之一：实心、横线、竖线、十字、斜线、圆环、网格、点阵。
图案画在取样框和音符面板上，并且作为音效播放。

分配不是按色相查表，而是一次图着色：把"在最差视觉下难以区分"的颜色对连成边，然后用 8 种
图案去染这张图。看上去像的颜色就拿到不同图案，而这恰恰是图案必须独自承载信息的场合。
结果：52 个颜色里只有 2 个和自己难以区分的邻居共用图案。

### 运行时混淆分析

启动时，程序会把每种色觉类型下完整的 52×52 模拟色差矩阵算好。运行时如果取样颜色在用户
自己的色觉类型下和另一个音难以区分，屏幕会说：

```
under deuteranopia this also looks like D4 (dE 4.2) -- go by pattern 'diagonal'
```

一个猜错了却不出声的工具，比什么都不说更糟，因为用户没法把这两种情况区分开。
把歧义说出来，能把注意力导向仍然可靠的线索：音效、图案、音名。

同一个思路还有一个与色觉无关的版本。如果取样颜色正好落在两个音中间，屏幕会报出到两个音
各自的距离："这个颜色卡在两个音之间：离 A3 3.1，离 B3 4.6"。

### 不会在色环上绕回去的平滑

颜色索引是环绕的，50 和 2 是同一个色相的两侧。按算术平均得到的是 26，一个屏幕上根本没
出现过的颜色。`palette.py` 在 CIELAB 空间做平滑，色相按角度取圆周平均，并剔除离群样本，
这样掠过采样框的手或阴影不会把估计值一起拖走。测试里专门钉住了这一点。

平滑的代价是约 8 帧的滞后，默认大约 0.27 s。这是故意的：不平滑的画面对着动一下就抖，
而抖出来的音没法弹。这个值由 `--smoothing` 调整。

### 不在灰度上瞎猜

灰、黑、白没有色相。照样把它们送进 52 个色相里比距离，你会得到一个自信但毫无意义的答案；
而用户看不出这个物体是无色的，也就无从知道这个答案是随便给的。色度（CIELAB chroma）
低于阈值时，程序判定没有颜色，保持静音，并在屏幕上说明原因。

### 不阻塞画面的音频

一件乐器要能弹，得满足两件事：一个音不能冻住画面，新音不能掐掉上一个音。

- 调度线程在渲染循环之外执行定时事件，所以采样播放、琶音和音效都是排队执行而不是 `sleep`。
  渲染循环永不阻塞。
- 通道池让音可以自然叠加，像一件带延音踏板的真乐器。
- 音量活在通道上，不在 `Sound` 对象上。这才是"每个音有自己的力度"能成立的原因：改共享
  `Sound` 对象的音量，会污染后面每一个音的力度。
- `--bank pure` 换成不含谐波的单正弦，音高最不含糊。对靠耳朵而不是靠音色辨色的用户，
  这是该用的音色库。

### Daltonize，以及它到底值多少

两个色觉滤镜都只作用于显示：

- `d` 增强（daltonize）把色觉缺陷丢失的信息搬进剩余的通道。
- `s` 模拟把预览渲染成选定色觉类型看到的样子，让正常视觉的用户能检查一个物体到底好不好分。

朴素的 daltonize 是"加上修正量，然后截断到色域内"。截断不是中性操作。在一对饱和红色上，
截断把修正刚刚制造出来的差异又抹掉了，色差从 5.03 掉到 0.00，也就是增强让两个本来不同的
颜色变得一模一样。本项目的实现按每个像素的剩余色域空间缩放修正量，收益略小一点，但绝不会
帮倒忙。

它到底值多少，实测如下：

| 调色板 | 可混淆颜色对 | 增强后色差中位变化 | 变好 / 变差 |
|---|---|---|---|
| `cvd_safe` + 红色盲 | 11 | +3.39 | 9 / 2 |
| 52 色相 + 红色盲 | 139 | +0.01 | 60 / 30 |

增强救不了一个本来就烂的调色板，因为用户需要的信息压根不在画面里，没法被重新路由。
有用的是选对调色板。Daltonize 是在好调色板上清理残余的难分颜色对，别的做不了多少。

有两条不变量是被强制的。增强只作用于预览，选音永远基于原始画面，否则"程序认为这是什么颜色"
会跟着一个显示开关漂移。滤镜代价与画面内容无关，这也是 `--filter-scale` 存在的原因。

### MediaPipe 打不开非 ASCII 路径下的模型

这件事影响每一个要安装本项目的人，所以说一下。只要 MediaPipe 的安装路径里含非 ASCII 字符，
包括中文、西里尔文、带重音的字母，甚至只是 Windows 的"副本"后缀，它的 C++ 层就打不开自己
带的模型文件，并对一个明明存在的文件报 `The path does not exist`。原生扩展在加载时就把资源
目录登记好了，之后再改 `sys.path` 没用。

`colorpiano/gestures.py` 在第一次 `import mediapipe` 之前检查安装路径，如果是非 ASCII，
就先把 MediaPipe 复制到一个纯 ASCII 的临时目录再从那里导入，按版本号缓存，只做一次。
另外，新版 MediaPipe wheel 删掉了自带的 `mp.solutions.hands` API，并且不含任何模型文件，
所以现在还需要额外下载 8 MB。两种 API 都支持并自动探测，自检会说明落在哪条路径上。
当然，把项目装到纯 ASCII 路径下仍然是更好的答案。

## 快速开始

```bash
git clone <this-repo> ~/colorpiano        # Windows 上可以用 C:\dev\colorpiano
cd ~/colorpiano
python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS / Linux:
source .venv/bin/activate

pip install -r requirements.txt
python main.py
```

Windows 上有一个脚本可以一次装完，并顺手下好可选的手势模型：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\setup.ps1
```

装到纯 ASCII 路径下，原因见上面那条 MediaPipe 说明。程序内置了绕过方案，但干净路径更好。

必需的依赖有三样：`opencv-contrib-python`、`numpy`、`pygame`。手势用的 `mediapipe` 和
语音报色名用的 `pyttsx3` 都是可选的，程序启动时会报告它找到了什么。

### 检查安装

```powershell
python main.py --selftest --skip-hardware     # 不碰摄像头和声卡
python main.py --selftest --pipeline          # 再加一遍端到端测试
```

## 使用

```powershell
python main.py                                          # 摄像头
python main.py --palette cvd_safe --cvd deuteranopia    # 色盲用户推荐起手式
python main.py --bank pure --announce                   # 最清楚的音高 + 语音/音效提示
python main.py --source synthetic                       # 合成测试画面，不需要摄像头
python main.py --source video --source-path demo.mp4    # 视频文件循环播放
python main.py --range chromatic --range-start 60        # 52 个半音代替 52 个白键
python main.py --record out.mp4                         # 录制带标注的画面
python main.py --filter-scale 0.25                      # 色觉滤镜更快（画面略软）
```

色觉障碍用户第一次上手可以用 `--palette cvd_safe --bank pure --announce`：调色板分离度最大、
音高最不含糊、每次切换都有音效或语音确认。

### 手势

手势是给腾不出手的场景准备的，从来不是必需品。每个手势都按整只手的姿态判定，以手本身的大小
为单位归一化，并且要连续保持若干帧才生效，所以它和摄像头距离无关，手一转也不会误触发。

| 手势 | 作用 | 触发方式 |
|---|---|---|
| 大拇指朝上 | 音量 +5% | 按住可连续调 |
| 大拇指朝下 | 音量 −5% | 按住可连续调 |
| 剪刀手 | 换音色 | 做一次触发一次，需先松手 |
| 握拳 | 停止所有声音 | 同上 |
| 张开手掌 | 暂停识别 | 持续 |
| 食指指 | 取样框跟手指移动 | 持续 |
| 捏合 | 取样框跳到捏合点 | 持续 |

## 性能

不开色觉滤镜时，程序在 1280×720、普通笔记本摄像头上实测约 30 fps，也就是摄像头本身的上限。
瓶颈不在这里。

色觉滤镜是唯一昂贵的部分，因为它们是逐像素的颜色变换，代价和画面内容无关。第一版把预览
从 30 fps 拖到了 3.8 fps，之后做了三轮优化：

| 优化 | 效果 |
|---|---|
| sRGB 传递函数改用查表，替换原来的逐像素 2.4 次幂 | 单帧 350 ms → 210 ms |
| daltonize 的四次矩阵乘法预合成为两次 | 微幅 |
| `_gamut_scale` 由 4 次归约改为 2 次 | 47 ms → 41 ms |

还有一次"优化"被测试拦住了：把增益上界改成更省的对称形式后，可分离的颜色对从 9/11 掉到
7/11，改动回退了。

最终采用的是 `--filter-scale`（默认 0.5），滤镜在半分辨率上计算再放大。辅助功能关心的是
颜色关系，降采样不影响它，而代价按平方下降。合成画面、两个滤镜全开时实测：

| | 帧率 |
|---|---|
| 不开滤镜 | 24 fps（合成源自身的上限；真实摄像头为 30 fps） |
| 两个滤镜，`--filter-scale 1.0` | 5.5 fps |
| 两个滤镜，`--filter-scale 0.5`（默认） | 15 fps |
| 两个滤镜，`--filter-scale 0.25` | 21.7 fps |
| 真实摄像头 + daltonize + 手势 | 27.8 fps |

也试过按横向条带分块处理以改善缓存局部性，完全没有差别，85.7 ms 对 87.7 ms，所以限制在
numpy 的吞吐而不是缓存。这些数字记在注释里。

另外两个取舍：平滑引入约 8 帧滞后，见上文；音色库按需构建，默认只加载钢琴库，52 个音约 23 MB，
按 `b` 切到合成或纯正弦时才生成。

## 已知限制

1. 增强（daltonize）效果有限。它救不了烂调色板，只对好调色板上的残余难分颜色对有效。
   起作用的机制是选对调色板。
2. 52 色相调色板有 52 分之 48 个条目存在双胞胎。这是那种摆法的固有属性，不是 bug，
   保留它只是为了让用户能亲耳听到对比。请用 `cvd_safe`。
3. 平滑有滞后，颜色突变后要约 8 帧才稳定。
4. 52 种颜色要学。音高只有在学会映射之后才能标识颜色。键盘条、颜色名称和图案音效是为了帮你
   度过这个阶段，但预期要练，而不是一上手就会。
5. `--range chromatic` 的黑键是变调借来的，用邻近白键录音变速得到。±3 个半音以内听感尚可，
   再远会明显变薄。
6. 手势在新版 MediaPipe 上需要额外下载模型文件，并且需要看得见的手。遮挡、逆光、手套都会
   降低识别率。
7. 语音报色名需要安装 `pyttsx3`。没装时会退回到图案音效，功能不缺失。
8. 靠音高辨色会受环境噪音影响，戴耳机效果最好。程序不会提醒这一点，得你自己发现。

## 背景

这是早期一个 `color_piano` 项目的重写版。重写的起点是发现原版的手势控制从来没有真正执行过，
因为 MediaPipe 打不开非 ASCII 安装路径下的模型文件。让人继续做下去的理由是另一回事：
原版的颜色匹配在 CIEDE2000 需要 `L∈[0,100]` 的地方用了 8 位 Lab 值，它那套 52 色相调色板有
48 个条目和一个邻居无法区分，而且它完全没有"我不确定"这个概念。

所以这次重写把颜色数学换成了一份经过验证的实现，把调色板从继承改成计算，并补上了歧义报告。
原版的那些缺陷不再在这里逐一罗列。留下来的两部分是还对读者有用的：上面那条 MediaPipe 的
可移植性约束，以及那些调色板测量数据，它们是"调色板为什么要算而不能挑"的证据。

原项目保留在原处，未做改动。

## 疑难排错

**启动就报"无法访问摄像头"**
检查是否被其他程序占用，比如会议软件或浏览器。换索引 `--camera 1`。或者先跑
`--source synthetic` 确认程序本身没问题。

**没有声音**
自检里 `audio` 一项会说明。找不到声卡时程序会自动切到静音驱动继续运行，所有逻辑照跑，
只是听不见，不会崩。

**音高不好分辨**
`--bank pure` 用不含谐波的单正弦，音高最清楚，靠耳朵辨色的话就该用这个。比什么都管用的是
戴耳机。

**手势不工作，启动打印 "could not start hand tracking" 或提示缺少模型**
两种可能，自检会说明是哪一个：

- 提示 `mediapipe 1.x is installed, which needs a separate hand model`：运行
  `python -m tools.fetch_model` 下载一次。
- 提示 `mediapipe cannot reach its own model file`：安装路径含非 ASCII 字符。程序会自动把
  MediaPipe 复制到临时目录绕过。若还失败，把 venv 建到纯英文路径，比如
  `C:\dev\colorpiano\.venv`。

**颜色总是认成旁边的那个**
调小 `--stabilizer` 让切换更灵敏，或调大 `--smoothing` 让它更稳。若屏幕提示
"under deuteranopia this also looks like ..."，说明这两个颜色对你确实难分，换
`--palette cvd_safe`。

**声音很怪 / 音不对**
`--velocity-from-brightness` 让响度跟随明度。想用恒定音量就用 `--no-velocity` 关掉。

**窗口里文字太小 / 对比度不够**
按 `L` 开大字模式。`--high-contrast` 加高对比边框。

**开了色觉增强/模拟之后画面变卡**
这两个滤镜是逐像素运算，代价固定。用 `--filter-scale 0.25` 换取帧率。辅助功能关心的是颜色
关系，降采样不影响判断，画面会略软。

## 项目结构

```
ColorPiano-Pro/
├── main.py                    命令行入口（参数解析 + 启动）
├── requirements.txt
├── assets/
│   └── notes/                 52 个音符 wav（A0–C8，88 键钢琴的全部白键）
├── colorpiano/                库本体
│   ├── config.py              路径、常量、Settings（所有可调项集中在这里）
│   ├── notes.py               音名解析、样本发现、补位、音域模式
│   ├── colorspace.py          sRGB↔CIELAB、CIEDE2000（34 组标准数据验证）
│   ├── colorblind.py          色觉模拟、增强、混淆分析
│   ├── palette.py             两套调色板、圆周平均平滑、滞回、颜色命名
│   ├── synth.py               WAV 读取、变调、合成音、图案音效
│   ├── audio.py               音色库、通道池、非阻塞调度线程
│   ├── vision.py              摄像头/视频/图片/合成 四种帧源、取样、白平衡
│   ├── gestures.py            MediaPipe 封装、姿态判定、去抖、路径修复
│   ├── hud.py                 全部屏幕叠加绘制
│   ├── announce.py            语音 / 图案提示音
│   ├── diagnostics.py         自检项
│   └── app.py                 主循环：把所有东西接起来
├── tools/
│   ├── selftest.py            安装自检 + 端到端管线测试
│   └── design_palette.py      色盲安全调色板的设计/复现脚本
├── tests/
│   └── test_core.py           67 个单元测试
└── scripts/                   一键安装 / 运行脚本
```

分层是刻意的：数值放一处，绘制放一处，硬件藏在接口后面，声音单独一个模块。
`colorblind.py` 里没有 UI 文字，`hud.py` 里没有颜色数学，`announce.py` 在模块层不导入语音库，
`vision.py` 把"从哪来帧"藏了起来。所以整套管线可以在没有摄像头、没有麦克风、没有语音引擎的
机器上被测。
